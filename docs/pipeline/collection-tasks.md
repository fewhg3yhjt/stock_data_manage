### 任务、运行、窗口与分区

任务定义生产目标，调度规则决定何时提交；自动到期和手动区间进入同一提交/准备合同。提交时解析并冻结数据集、K线周期、目标日期集合、各日期证券身份范围和来源策略，按来源能力生成请求窗口和实际条数。1日和100日是范围输入，不在Provider中分别写常量。请求窗口可以跨多个交易日，解析后按业务日期构建候选；正式结果仍按交易日期、资产类型发布。已确认的旧运行冻结原则不变，改目标或参数须使用新运行。

### 用户确认的五项行为

| 项目 | 已确认合同 | 用户可见后果 |
|---|---|---|
| 执行顺序 | 整项任务先到先执行，其余等待；不采用窗口交错、自动任务抢占或多任务并行写入 | 手动长任务可能推迟自动任务，页面显示等待及前序任务；排队不能把原周期目标日期改成实际执行日期 |
| 活动范围 | 等待中和运行中的任务都占用范围，重叠任务拒绝提交 | 不能先将冲突任务排队，再等它取得隐式覆盖权；检查与登记须在一个受协调的提交边界完成 |
| 重叠定义 | 同一数据集和K线周期下，目标日期与证券身份范围都相交才算重叠；证券范围按对应日期判断 | 同日分别采茅台、平安银行不构成业务重叠，可提交后按FIFO等待；最终仍写同一日期分区，不能因此并行改文件 |
| 已有数据 | 已有正式结果覆盖本次目标时，列出重叠日期与对应证券范围；未勾选“覆盖执行”不得继续该重叠请求 | 覆盖只授权本任务选中的重叠范围，保留其他日期/证券；覆盖勾选不能绕过活动任务冲突或质量与发布门槛，不采用默认只补缺策略 |
| 发布可见性 | 普通区间任务按日期发布，允许部分完成，失败日期保留问题及恢复位置 | 失败日期不替换原正式结果；任务可同时有已发布和未完成日期。历史复权换版的跨日期一致性继续由[历史重建合同](daily-history-rebuild.md)规定 |

同日不同资产类型先按证券身份区分，证券代码承接沿现有稳定身份合同处理；不能把改码前后同一证券当作互不重叠。不同数据根的隔离验证不因日期相同占用正式运行范围。

预览不是最终授权：从提示到正式提交期间，其他任务可能占用范围或发布数据，服务端必须再次检查。发生新增重叠或重叠范围变化时，返回变化内容重新确认，不能复用旧页面的覆盖勾选授权新增日期/证券。进入等待后原目标不改变；FIFO使先提交任务先完成，下一个运行按自己的冻结范围和覆盖意图执行。

自动任务也遵守活动重叠拒绝：若某手动运行已占用本周期范围，本次自动提交显示被哪个运行阻挡，不能标成采集成功；自动调度规则不因此被停用，下一周期照常判断。不因拒绝便每轮重复请求来源，也不把它静默改成补缺/覆盖任务。停止调度只阻止后续触发，已经提交的运行按冻结合同处理；取消当前或等待运行不属于本次已明确的功能范围。

### UML交互时序：提交到按日期交付（目标，待实现）

下图将提交协调视为现有pipeline/worker的职责，不引入新服务。来源请求可覆盖多个日期；原文先保存再解析，各日期从同一批候选取数。整任务执行权保持到本次运行结束，日期发布不触发下一任务插队。

```mermaid
sequenceDiagram
    autonumber
    participant E as 运行台、CLI或自动调度
    participant S as pipeline提交协调
    participant M as 运行元数据
    participant W as worker与任务执行器
    participant P as routing与Provider
    participant R as raw证据存储
    participant B as daily构建与质量检查
    participant C as canonical当前分区
    E->>S: 日期范围、证券范围、任务配置
    S->>M: 检查等待及运行占用
    alt 日期与证券同时重叠
        S-->>E: 拒绝并列出日期、证券及占用运行
    else 无活动重叠
        S->>C: 检查范围内已有正式数据
        opt 存在已有数据
            S-->>E: 列出重叠范围，要求覆盖确认
            E->>S: 勾选覆盖后重新提交所见范围
        end
        S->>M: 协调边界内复核、冻结并登记等待及占用

        M-->>E: 已接受及FIFO等待位置

        Note over W,P: 执行器按来源合同规划窗口及条数，Provider只执行协议获取
        loop 每个请求窗口，遵守来源限速
            W->>P: 该窗口的证券、日期、条数及来源参数
            P->>R: 保存完整实际响应及请求清单
            alt 响应及证据持久化成功
                R-->>W: 原文引用
                W->>B: 原文引用，经对应Provider解析、标准化为批候选
            else 获取或持久化失败
                W->>M: 记录失败窗口及受影响范围，不伪造候选
            end
        end
        loop 每个目标日期及资产分区
            W->>B: 该日期候选、冻结证券范围及发布规则
            alt 达到发布门槛
                B->>C: 锁内读取最新分区并替换本次授权证券
                Note over B,C: 保留其他证券，只保留当前正式行情；不建立旧行情快照
                C-->>M: 记录本日期发布结果及当前分区引用
            else 日期检查不通过
                B-->>M: 失败原因、证据及恢复位置
                Note over M,C: 本日期正式分区不变，其他通过日期继续发布
            end
        end
        W->>M: 汇总本次成果、失败及未完成范围
        Note over W,M: 提交中断先按既有提交恢复合同处理，不能直接释放
        W->>M: 结束本次运行并释放占用，进入下一等待运行
        M-->>E: 逐日期状态及当前数据入口
    end
```

没有覆盖授权时不登记运行；自动提交同样不能隐式取得覆盖权。获取失败或证据落盘失败按现有错误合同记录，无法形成有效候选的日期不能进入成功发布分支。图中等待登记、取首任务及恢复协调尚待实现；不是对当前并发安全性的证明。

### 设计演绎与尚需收敛的点

| 场景（说明用例，非本次实际任务） | 按确认合同推演的结果 | 不能静默采取的行为 |
|---|---|---|
| A等待或执行11月2—5日茅台，B提交11月5日茅台 | B因日期与证券交集被拒绝；页面显示A及重叠范围 | 将B悄悄排在A后自动覆盖 |
| A执行11月5日茅台，B提交11月5日平安银行 | B可提交并等待；完成A后B在锁内合并当天分区 | 只因证券不重叠便并行写同一Parquet，或用B的小分母覆盖全分区统计 |
| A是老日期长任务，B是今日自动任务且范围不重叠 | B等待A整项结束；B的目标日期保持原周期日期 | 自动任务抢占A，或执行跨日后改抓第二天 |
| 茅台目标日已有数据，提交未勾选覆盖 | 提示具体日期/证券并不提交；勾选后仍重新检查活动冲突 | 默认跳过已有记录、复用旧勾选覆盖新出现的数据，或替换其他证券 |
| 区间前60个日期已发布，第61日失败 | 保留前60日成果与失败位置；运行显示部分完成，按冻结范围恢复 | 把整个区间标成功，或将旧数据伪装成本次新成果 |
| 覆盖任务某日期未过发布门槛 | 原日期正式结果保持；其他通过日期可发布 | 先删旧分区再采集，或因勾选覆盖就降低质量门槛 |
| 覆盖日通过现有允许少量缺失的门槛 | 仍按已有发布合同处理，明确本次缺失和原目标 | 悄悄拿旧值补齐新采缺失并声称本次完整成功 |

任务整体失败与某分区处于committing须区分：待提交恢复标记仍按既有恢复合同处理，不能仅把任务状态改失败就释放其未完成提交。候选批文件共享行、raw共享引用、共享索引及来源限速需在实施方案明确承接；封包格式和批大小属于待收敛的物理方案，不能因此新增任务管理层。

2026-11-08进一步确认：只覆盖本次选中的日期和证券，其他证券保留；正式行情不保存旧快照，旧运行展示当时记录及当前数据入口；各状态产物不设置保留期限，本轮不实现自动清理或清理模块。存储与查询影响分别由[存储说明](../storage/README.md#物理优化及本轮不做的清理)及[运行台合同](../service/read-only-web.md#区间提交等待和覆盖交互2026-11-08确认待实现)维护。这些不再列为待决策项。

当前仍缺区间生产、等待/占用与覆盖确认实现，后续正式开发需按本合同列出具体模块改动和定向验收；本节不授权删除旧文件、迁移生产数据或启用新的调度行为。

| E 调度与页面：`config/schedules.yaml`、`src/worker/scheduler.py`、`src/service/web.py`及`static/` | 当前停用任一业务schedule会被当作required missing；改成停用仅阻止其后续提交，其他调度继续。区间/覆盖输入及范围冲突 → 等待/逐日期结果；停止调度 → 配置保存结果 | 停调不取消已接收任务；等待跨日仍保留原周期。新增或受影响API逐路由覆盖成功、空结果、错误、冲突、分页及副作用边界；性能预算在接口方案中与代表性规模一并列明，不能只测HTTP成功 |

以上A—E是依赖划分，不要求开五个代理或五套入口。A可先独立消除单日过量历史请求；B明确多日期数据结构；C修改共享批文件后覆盖直接调用方及查询；D在并发合同收敛后接入；E使用同一提交路径。每阶段按影响完成一次定向验收和必要端到端，再设计对照、更新现有进度、提交；不等到末尾才记录偏差。

### 执行循环与入口的承接（2026-11-09已确认，实施中）

数据库只保存等待事实，不会自己执行任务。沿现有worker模块提供同一个取队首/执行循环：scheduler的到期轮询只负责受理，由其执行线程消费；允许写操作且数据根可写的Web实例在自身生命周期内保持一个执行循环，替代每次POST直接执行指定任务的方式，只读Web实例不参与消费；CLI正式采集入口也先受理并等待/驱动同一FIFO。它们可以同时存在，但只有取得现有整任务执行权的一方实际执行，不增加新服务、消息中间件或另一套内存权威队列。

执行循环在空闲时采用有限间隔检查（草案1秒），提交后可通知同进程循环提前检查；跨进程仍靠持久队列检查，不以一次线程唤醒作为交付保证。循环退出/进程关闭前后新提交的运行仍留在库里，其他存活循环或下次启动能看见；没有运行中的执行进程时，受理成功与开始执行必须分开显示。调度轮询继续按既有有限间隔判断到期，不能被网络线程阻塞。

进入下一普通运行前先处理已确认原执行者退出的committing恢复；浏览器关闭不停止后台，Web后端正常停止与强制退出分别沿既有生命周期/恢复合同，不凭前端断开释放执行权。该承接改变现有Web/CLI直接执行方式，已获用户确认，但必须用实际运行证明，不能仅配置一个队列状态就宣称拥有后台消费能力。

| 请求限速与原文 | 协调器先创建来源组要用的原文/归档父目录；传输层再将`requests.Session`请求钩子分派到各自线程的捕获上下文。原文及manifest逐请求、逐证券单元保存；共享`RequestPacer`按主机限速，批协调器独占更新单元状态、进度和检查点 | 两个Provider的响应不串档；Windows下不让工作线程竞争创建共享目录；同一物理主机不会因为不同来源组各建限速器而放大请求速率 |
| 交错处理 | 协调器把每个来源组刚完成的单元送入容量32的有界队列；单个处理线程立即按匹配Provider解析、归一化和校验，网络采集继续按来源合同运行 | 内存积压有界；解析错误只标记对应单元，保留原始响应，其他单元继续。原始捕获仍按证券×口径请求，不改变来源和限速 |
| 候选与查询索引 | 每50个处理单元或队列空闲1秒，将成功候选按资产类型和来源输入写入一个Parquet批文件；同一批次的来源报告在SQLite中一次事务提交。逐单元manifest、报告和来源行仍保留，索引选择器仍覆盖完整来源行 | 断点单元用批文件路径和行号定位；已发布候选在汇总时每个批文件只校验、读取一次。查询API继续读取相同的报告、选择器和来源行，保留分页和筛选口径 |
| 合并与发布 | 各Provider产生的标准候选在`prepare_daily_task_publication`汇合，统一做身份、日期、口径和覆盖检查，再按证券类型走现有发布 | 同一任务仍只生成按日期和资产类型聚合的日线分区；来源证据按记录保留`source_provider`及对应原响应引用，不建“腾讯发布/CSI发布/CNI发布”三条数据路线 |

当前来源输入都是单组内顺序请求：腾讯日线间隔`0.3秒`；CSI与CNI日线间隔`3秒`，配置均为`effective_concurrency=1`（见`config/providers.yaml`中的`ASTOCK-002-daily`、三个`CSI-INDEX-DAILY-*`合同和`CNI-INDEX-DAILY-001`）。不同来源组可并发调度；CSI收盘、CSI四价与CSI配对收盘合同共用CSIndex主机请求限速，不会绕过来源或主机限制。新增来源是否允许正式在线请求，仍由资格检查决定。

本批来源组由冻结的`input_id`决定：腾讯日线、CSI直接收盘、CSI并列码完整四价、CSI并列码收盘序列、CNI完整四价。它们不是“一个证券一条流水线”。资格和健康状态由协调器在请求前检查；工作线程每完成一个请求都会等待协调器记录原响应及单元状态后再继续，因此403/429等状态更新会在该来源下一次请求前生效。协调器把已完成响应加入有界处理队列后即释放来源线程，处理线程可在后续请求进行时解析前一单元。候选Parquet每批最多50个成功单元，队列空闲1秒时刷新尾批；SQLite索引对同批报告共用一次事务。单元失败保留独立原因，不停止其他来源单元；程序异常停止后续请求并走现有恢复流程。

#### 并发、检查点与失败行为

| 设计点 | 目标合同 |
|---|---|
| 调度粒度 | 工作单元仍是冻结的日线请求单元；调度器按来源合同分组并并发运行，不把一个证券的采集、解析、发布串成小流水线 |
| 并发上限 | 每个冻结`input_id`组由一个工作线程顺序处理；来源组之间可并发。当前日线捕获按主机并发1、配置间隔限速；共享物理主机的来源组复用同一个`RequestPacer`策略 |
| 结果写入 | 请求工作线程只返回单元结果及原文引用；由批任务协调器统一更新单元索引、进度和检查点，避免多个线程竞争改写同一批次状态 |
| 局部失败 | 单元网络失败或解析失败记录在本单元并继续其他独立单元；某来源组不合格或失败不触发另一来源自动替代。全部采集和排队处理到达终态后，覆盖门槛决定能否发布 |
| 系统错误 | 原文持久化或共享任务状态损坏属于批次级错误，应停止后续采集、保留已有证据并走现有断点恢复，不得伪装为来源失败后继续发布 |
| 恢复 | 已成功且原文完整的单元复用；失败/未完成单元按原冻结范围续跑。已捕获的来源不因另一来源失败而重新请求 |

所以本阶段实现的是“现有批任务中的按来源输入调度、来源专属解析、统一候选聚合”。CSI/CNI原始响应的隔离重放证明代码路径与数据汇合合同可执行；它不替代实时语义认证或在线资格。正式在线采集仍会在请求前被现有资格规则拦截。

冻结定义只写一次；既有请求级清单和单元manifest保存本条结果，任务元数据和summary只保存定义引用、阶段计数及产物引用。单元清单是恢复结果依据，摘要供显示。恢复按冻结计划核对产物一次，正常逐条执行不重写整份定义或已有报告。原文在采集阶段取得稳定归档引用，活动raw仍仅在完整分区发布后转正。已有原文仅按明确范围、时效和完整性复用，原始采集时间不改写。

旧日线检查点只读保留，不由新执行器隐式接管；用新任务与隔离根复用原文验证。历史查看保留，生产执行收敛为一条批路径。完整scope及规则变化必须新任务。现有原文、旧报告和正式data不迁移或覆盖。

配置中的`market_daily`声明股票、ETF、指数三种类型，`universe: all`从目标日之前最近的已发布证券名单中选择这三类，沿用上市/退市日期及未上市过滤；最终名单与请求在首次执行冻结。`stock_daily`继续表达同一批执行器的股票范围子集。离线请求须逐口径提供`replay_manifests`，live任务不得用离线原文覆盖请求；可在任务定义的`evidence_roots`列出既有原文目录，执行器一次扫描，只有精确请求、有效期及字节完整性符合原缓存合同才复用。没有匹配原文才联网，限速与来源协议不变。

```json
{"task_id":"market-daily-20261029-batch","task":"market_daily","trade_date":"2026-10-29"}
```

以上任务文件仍从`collect-task --task-file <文件> --mode live --data-root <隔离运行根>`进入；隔离根必须已有已发布名单及匹配的来源资格。它不会自动启用调度、补造日历或缩小未认证范围。准备失败不发请求；来源资格按授权证据分组校验一次，物理请求前检查到期与冷却。原文获取成功不等于行情处理成功，解析失败留在处理阶段，不自动返向补采。续跑先核对冻结定义、原文和已处理产物；完整性损坏明确阻断，不能拿旧发布结果伪装通过。`--redo full/selected`是显式重做，保留旧尝试，不改变冻结证券及规则；输入范围变更使用新任务。

现有归档命令已适配批记录：只有完整发布、原文/候选/报告/规范分区校验通过才移动工作区，更新运行索引中的位置；冻结定义与原始报告字节不改写。已归档任务可只读续跑确认，重做使用新任务。旧单输入collector测试入口只服务证券名单，日线测试直接驱动独立采集/处理操作和真实响应格式，不保留第二条生产路径。

接口支持字段选择时，采集合同应请求接口公开的完整字段集合；接口不提供字段选择时，保存它实际返回的完整响应。字段映射只在解析与标准化阶段选择数据集所需字段，来源行保留全部实际返回列。接口未返回的字段不能靠本地映射补出。BaoStock日线验证路径的合同是：先在 socket `recv` 边界保存每次查询返回的有序原始字节，再保存完整SDK解码 `fields/rows`，之后Provider才提取标准候选字段；请求范围及响应哈希关联两种记录。重放必须精确匹配查询参数和来源版本，并只从归档的解码结果重建SDK结果，不允许缺档时联网补取。该路径仍属于 `validation_only`，不进入当前正式日线任务；捕获/回放合同和历史证据范围见[来源接口说明](../providers/README.md)。

名单任务预定义的多个互补来源会分别采集，解析后合并；不会因为普通ETF目录不足才动态追加另一来源。对同一采集包的切源，从新来源重新取得完整包，不把两家来源的失败分页拼在一起。传输阶段允许必要的会话、分页控制与SDK解码，不用OHLC、字段完整度或证券覆盖判断是否换源。

| 来源不满足请求前资格或参数 | 明确阻断，不绕过 | 不请求不合格候选；无可用来源则阻断 | 留下具体原因，不视为试采成功 |
| 连接失败、超时 | 按来源合同有限重试后失败 | 仅配置允许时尝试下一来源 | 保存失败尝试，不能声称来源业务不支持 |
| 指定的HTTP故障状态 | 有限重试或失败，不换来源 | 仅 `switch_on` 列明才切换 | 保留响应与状态；限速冷却仍有效 |
| HTTP成功但HTML、无效JSON、空业务数据 | 接收后结束采集策略 | 接收后结束采集策略 | 解析及检查产生问题，不自动切源 |
| 日期、单位、价格或覆盖异常 | 不改变已选来源 | 不返回采集循环 | 报告到实际来源、记录及字段，按原门槛决定发布 |
| 程序异常、无效配置或证据落盘失败 | 直接报错 | 不伪装成可切换网络故障 | 保存可保留的诊断，不能继续处理未落盘响应 |
| 完整原响应存在，转换失败 | 可复用响应重处理 | 不因 `resume` 自动选下一来源 | 修改规则仍须明确版本与验证 |
| 用户看过明细后明确要求重采 | 按指定来源执行 | 按明确选择的自动策略执行 | 这是新采集操作，保留此前结果与证据 |

一项任务可以返回“采集接收完成，但解析或质量未通过”。来源是否请求成功、数据是否有效、任务是否发布分别记录，不能折成一个成功标记。问题字段由总体设计单处维护，现有输入报告、检查结果和任务摘要通过引用关联；不额外维护前端状态或第二份明细报告。

### 恢复与实现边界

执行记录保持必要的冻结范围、实际来源、原响应引用和阶段位置。采集未完成时可按明确故障继续；原响应已完整保存时，优先处理原响应；发布中断只续接已准备的提交。数据结果一旦发布即可独立消费，不依赖任务进程或运行记录是否正在展示。

实施按现有 `collect-task` 入口收敛；不增加一套并行任务入口。配置版本冻结在任务定义中，规则变化要求新任务标识。离线验收不触碰正式数据目录。

现有日线任务首次从不晚于目标日的正式名单展开范围，并保存定义；已有任务由 `_task_units` 读取原冻结单元，不因新上市证券改变续跑范围。规则或请求合同变化仍要求新任务；不能将当前YAML覆盖旧定义。动态范围all_stock/all_etf/all_index只表示展开能力，不授予对应资产生产资格。

## 原始数据与任务的边界

数据日期与执行日期分别记录。历史证券清单任务使用 `collection.yaml.security_master.historical` 中支持目标日期的来源；其必需组与正式证券主数据一致，覆盖沪深股票、北交所股票、沪深ETF及沪深指数七组。BaoStock历史候选输入负责沪深股票和指数，北交所及ETF继续由已配置的目标日来源补足；任何必需组缺失时不发布，也不将当前目录改标成历史名单。历史发布验收可以在之后执行：支持历史日期的接口按目标日查询，只返回当前目录的接口必须使用目标日留存的原响应。自动调度按实际运行时间判断到期和日历，与指定历史日期的回放验收是两种执行方式；回放仍使用隔离运行根目录，不因此解除生产目录写入限制。

全量重做仅清空目标日期、本任务的活动暂存和构建文件引用，强制重新执行全部来源单元。新结果完整、检查及发布完成后替换该日期、范围的结果；失败时原已发布结果保留，不能拿旧正式记录补齐新采集的缺失。在线执行时绕过原响应缓存；离线验证始终回放明确指定的证据。清理前沿用既有归档保留响应证据，不改变其他日期，不在本次增加自动删除。

断点重做在同一数据日期、任务范围内根据哈希、字段合同、处理版本、单元检查和任务阶段判断：响应合格而后续失败的继续处理；请求失败、缺失或响应损坏的补采；合格处理结果直接复用。指定证券重做只重采该日期的指定证券，名单接口不支持单证券请求时拒绝该操作。新响应先进入该日期的暂存区，提取、合并并按业务主键去重后重新检查；合并的是派生记录和响应引用，不拼接修改原始响应字节。成功后替换受影响单元的当天引用，保留当天未重采部分及其他日期。

## 三阶段进度

既有任务统一使用 `worker/progress.py` 的 `TaskProgress`，不新增调度服务或状态数据库。`summary.json.progress` 和元数据库任务状态保存原响应、解析映射、检查发布三阶段的 `total`、`completed`、`success`、`failed`、`skipped`、`reused`、`percent`、`success_percent`、`elapsed_seconds`，并保存本次执行总耗时和开始时间。

三个阶段统一按本次来源单元计数：日线为证券×口径的来源单元，名单为来源接口；完整证券覆盖另以冻结证券数计算，不把接口页数或返回行数当成证券覆盖率。采集和处理的百分比是已处理数量，成功率另计；失败全部处理完可以达到100%，不能据此判断任务成功。总量未知时百分比为null。日线原响应采集和解析处理通过容量32的队列交错执行；候选每50个处理单元或队列空闲1秒刷新，状态摘要仍最多每5秒保存一次。检查与发布按整批提交统计：两只股票三口径共六个单元，提交完成前为0/6，完整提交结束后为6/6；检查拒绝为失败、0/6，不因完成内部动作而增加百分比。检查、规范文件、原响应转正、元数据收尾只保存为动作状态及恢复依据，控制台显示最近动作。恢复重复动作不重复累加，旧版四步骤快照恢复时以原响应阶段的总量重新计算；历史已保存证据不批量改写。使用前次正式结果回退时，完成数量计为复用。

## 持久化记录

任务 DuckDB 保存任务定义、阶段、单元结果、错误及提交信息；一次名单提交的 `prepared-security-master.json` 保存在任务工作区，作为中断恢复时固定的候选输入，不会被日线或Web目录读取，也不作为按日Canonical发布。当前证券主清单由现有 `SecurityMasterStore` 保存于 `canonical/security_master/current/security_master.duckdb`，旁边的 `manifest.json` 记录最新成功更新日期、来源响应引用和数据库哈希。清单的字段变化写入该库的 `security_master_history`，代码别名写入 `security_symbol_history`。消费者各自明确：任务和恢复读取任务状态及固定候选；日线准备与运行台证券名称查询读取当前证券主清单。

原始响应与派生产物仍校验真实字节哈希。`complete_today` 表示本次全部配置来源单元和覆盖检查通过，不表示独立证明全市场覆盖。当前必需组是沪深北股票、沪深ETF、沪深指数七组；这些组有数据只证明本次来源并集覆盖了配置组，不证明各组完整。来源不完整时保留失败证据，不写当前库、不更改有效状态；成功后才按完整来源并集更新记录。

### 每日名单更新与当前有效状态

证券清单仍以 `instrument_id` 合并不同来源，ETF可由互补接口提供，指数仍以同一清单中的 `asset_type=index` 表示。没有指数专属清单目录，也没有每日一份规范全量名单分区。已存在的 `canonical/<日期>/security_master/` 保留为历史文件，不再作为新任务发布目标；当前数据库缺失时，读取器可用最近一份已发布分区引导首次更新。

完整性条件来自 `config/datasets/security_master.yaml`：全部配置来源单元成功、必需市场/类型组有记录且无分类冲突，才允许更新当前清单。某来源失败、空组或资格不足时，只更新本次任务状态和 `coverage.json`，当前 `security_master` 数据库与manifest保持原样。由此，没抓到名单不会让现有有效证券被标记为无效。来源并集完整成功后，旧清单中本次未出现且属于本次覆盖组的有效证券标为 `status=delisted`（当前无效），不推算 `delist_date`；以后在完整并集中重新出现时恢复有效。

日线任务在目标日尚无成功更新的名单时，会先调用既有证券清单任务。更新失败后，只有 `as_of_date` 不晚于目标日、且必需组齐全的当前或保留历史名单可以继续供日线使用；如果当前清单日期晚于目标日且没有可用的目标日前历史名单，不把未来证券名单用于过去的日线任务。成功生成日线任务定义时，把所用证券范围冻结在该任务的 `task.json`，续跑不会因名单后来更新而改变范围。

## 发布与恢复

1. 采集并持久化原始响应，再解析映射；失败和空返回也留下证据。
2. 保存各单元的合格候选，即使整体覆盖度不够也不丢弃成功单元。
3. 构建结果、检查覆盖和业务唯一键。日线沿用 YAML 中的质量与发布阈值；目标范围替换与跨来源冲突处理明确区分。
4. 提交前保存候选发布文件、来源哈希及最终位置，固定本次提交内容。
5. 执行发布和 raw 转正的收尾步骤。它们不是一个文件系统事务；只在全部完成、引用核验后标记已发布。
6. 中断时按提交记录恢复，不再请求接口。恢复未完成时拒绝全量清空或改变任务定义。正式分区内存在 `task-commit.json` 时查询和其他任务写入均拒绝；进程已结束的锁可回收，仍在运行或无法证明已结束的锁保留。

中间阶段保留单元状态、基础合同及错误以支持重做；最终覆盖及有效性汇总在发布前生成。复用任务 `coverage.json`、DuckDB状态及正式清单，不增加覆盖管理层。统一摘要已实现，字段与读取方式见 [自动任务摘要](#自动任务摘要)。

证券主数据复用既有证券标识、来源合并和日线记录模型。当天来源全集成功且必需分组有数据时，旧名单中未出现的证券标记为 `delisted`（不推断 `delist_date`），再出现时按当前来源恢复有效。日线展开时过滤此状态。源头目录更新不自动改写其他已发布数据；来源失败或必需组缺失时保留工作区，正式数据不更新。

## 验收

- 正式业务通过实际 `collect-task` 或证券清单调度入口运行；原响应、中间数据、报告、任务状态及发布结果位于业务运行根目录，`provider_validation/` 只被读取。
- 不同数据日期使用不同raw位置；同日全量重做替换当天结果，断点及指定证券重做只更新受影响单元，重复运行无重复业务键。
- 今天补采历史日线仍按目标数据日期保存；当前目录接口按原响应采集日期保存，不能伪装历史名单。
- 采集失败、有效性失败、覆盖不足、后续构建失败后，重启并断点续接。
- 全量不复用旧候选或旧源响应；指定证券只请求选中证券。
- 重复采集不增加重复业务键；全量范围替换不夹带旧记录。
- raw 转正前后和发布步骤间故障注入，恢复后文件、哈希和元数据一致。
- 原始数据损坏、候选损坏、路径越界、相同范围并发执行、定义变更被正确拒绝或重新处理。
- 已有真实来源证据的证券快照和日线离线端到端回放；夹具验证和真实证据验证分别标识。

### 配置和入口

复用现有调度、元数据、路由和任务流程，不增加任务管理服务。`config/collection.yaml` 的 `security_master.source_inputs` 指定一份清单的来源并集：`SDA-BOARD-005` 获取沪深股票和深市ETF，`SECURITY-BSE-001` 获取北交所股票，`SECURITY-SSE-ETF-001` 补接上交所上市ETF目录，现有 `SECURITY-BS-UNIVERSE-001` 提供BaoStock证券全集中的股票与指数记录。没有引入新Provider；现有三个现时目录来源没有指数覆盖，所以用户确认将已存在的BaoStock证券全集输入加入当前清单。证券身份按 `instrument_id` 合并，字段仍由原数据集模板和归一化映射管理。这些来源因配置在清单任务内而作为固定来源单元执行；资格记录仅用于动态来源路由，不决定这些明确配置的来源是否请求，也不授予它们用于其他任务的动态路由资格。

本入口只完成一次检查，不启动常驻进程。既有调度运行器可调用它；本阶段没有安装或启动后台服务。正式调度不接受回放模式、指定证券范围或验证输出目录；隔离回放继续使用 `collect-task`。日线到期执行会先检查目标日是否已有七组齐全的正式证券名单；若没有，使用同一入口先跑一次证券清单任务，只有发布成功才继续行情批任务。21:31或手工补跑仍属于当天到期任务，不要求恰好在16:20启动。清单来源请求或覆盖发布失败会停在对应阶段并把名单任务状态放入日线调度报告。

### 正常、失败和重试

1. 检查日期、采集配置和交易日历，按 `security_master.source_inputs` 生成 `security-master-YYYYMMDD` 任务，用户不选择来源文件。
2. 每个显式来源单元按自身请求合同获取数据。原响应先存入 `data/raw/_tmp/<数据日期>/<来源>/<接口>/`，再解析、映射和检查；HTTP 403/429等真实响应仍记录到既有来源健康状态。
3. 检查当天七组和日期一致性；全部配置来源完成后合并成一份名单。前次有效证券本次未出现时标记为 `delisted`，不推断退市日期；以后再次出现时恢复有效，再发布并完成raw转正。
4. 来源单元失败、必需组为空或分类冲突时记录具体问题，不发布部分来源结果；整份旧名单回退只处理来源或覆盖失败，不因单只证券消失而触发。
5. 再次执行同一天的入口沿用同一任务：只补失败或不完整来源，合格当天单元复用；完整任务校验后直接返回。回退任务不会被误判为当天完成。
6. 发布中断时沿用原提交恢复流程，不重新采集。全量与指定证券重做仍使用既有任务操作，详见 [当前入口](#当前入口与冻结范围)。

以上描述当前任务逻辑；2026-10-11简化目录实现及已完成的旧业务迁移见 [存储说明](../storage/README.md)。正式开发后的来源复核和发布验收通过业务运行布局留存，不向 `provider_validation/` 新增产物。

### 自动任务摘要

中间阶段保存基础有效性和单元状态。任务自动写入 `data/task_workspace/<日期>/<数据集>/summary.json`，结果中的 `summary` 返回路径和哈希，并保存到既有元数据库；调度也返回该引用。页面读取摘要，无需扫描接口目录或另跑覆盖脚本。同一工作区表示最近执行；更早任务按元数据及审计追踪。

摘要关联证券范围、请求日期、已发布数据日期、原响应采集时间、各来源数量、最终检查、缺失单元、失败原因、回退及发布清单。未发布时 `data_date=null`；发布中断为 `committing`、`pending_recovery=true`；整份回退保留原实际日期，并显示本次检查失败。全重做失败时不会把前次发布结果误写为本次成功。

失败后断点重做更新同一摘要，只重新采集缺失或无效单元；发布提交中断则沿用既有恢复流程，不请求来源。日线覆盖率的分母是本任务冻结证券范围，不是整个正式分区。证券名单没有可靠独立市场分母时，摘要仅列分组数量、缺失和检查依据，`denominator`、`ratio` 为 null。回放的 `verification_mode=replay` 必须与真实业务发布区分。

来源新返回HTTP403或429时记录到既有来源健康状态，后续请求受禁用及冷却检查约束。回放和缺少资格本身不记作真实接口限流。

## 进度显示与断点保存

进度回调只更新内存计数和显示，不写任务数据库。每个单元的原始状态、报告仍独立落盘；候选单元在所属批文件写入及查询索引批次提交后更新为完成，单元记录保留批文件路径和行号。完整summary.json最多每5秒生成一次，单元失败、检查阶段、发布阶段和任务结束立即更新。摘要生成负责一次状态保存，调用方不重复写入。元数据保存仅查询既有definition_hash验证任务定义不可变，不为此反序列化整份旧状态。

发布前保存committing及完整提交计划，规范文件和raw转正后的关键状态分别持久化；最后的published状态、完整进度和摘要成功保存后才移除发布标记。已有故障恢复规则保持。

候选续跑检查冻结任务、配置、原响应和候选数据完整性，不比较代码指纹。已有单元的revalidation_report若用于证明派生结果一致，仍须满足同一原响应、相同请求和全部映射字段一致；不再因源码变化要求生成该报告。原始来源报告保留原版本，不被改写成新代码的在线调用；失败或缺失单元仍走现有重做流程。

## 分钟与派生的独立合同

分钟组件有独立实现，不属于当前collect-task支持的数据集。下列规则保留为组件合同，不能据此声明已持续生产。

### 收盘快照与日线校准

包含开高低、当前价及量额的收盘快照可形成当日 provisional 日线，不能补历史日，也不能直接认证 final 或前复权完整历史。收盘缓冲、次日回看最近交易日和校准时间由 YAML 配置，不在说明中固定运行时刻。全市场快照默认盘后按天采集，允许已有配置按天或分钟指定间隔，不因分钟聚合设计而默认开启全市场盘中轮询。

### 分钟采集、热数据与盘后校准

- 盘中优先使用已验证的原生分钟能力；快照聚合只在明确启用、吞吐量合格的观察池内作为 provisional 路径，不作为全市场分钟默认方案。TDX等延迟来源的实际时效逐条记录，历史小样本不能代替当前资格。
- 单轮预算按批次数、有效并发和请求间隔估算：`ceil(symbol_count / max_symbols_per_request) / effective_concurrency × request_interval_seconds`。启动及观察池扩容均检查最大证券数、采集周期和 `cycle_deadline_seconds`，超预算拒绝，不静默降低时效。
- 累计快照的单分钟量额使用相邻边界差分；处理首根缺前值、跨日和午间重置、负差值、采样缺口、乱序、重复及迟到修订。采样不足标记 `incomplete_sampling`，保持 provisional，不能认证真实分钟高低价完整。
- 当天分钟通过 SQLite WAL Hot Store 持续写入与按业务键更新，来源可见且分钟闭合后即可查询，不等待 Parquet 导出或 WAL checkpoint。查询合并历史 Canonical 和当天 Hot，按键去重排序，返回质量、来源延迟和 `as_of`。
- 盘后将 Hot 与合格历史分钟标准化、合并、检查后发布 Parquet；只有交易时段、预期根数、时间、单位、重复和异常检查通过才能提升 final。预期根数按交易日历和时段配置计算，常规240根只是配置基准，不能把所有证券和日期永久写死为240。
- 5m优先由同一交易时段内完整、已确认的五根1m生成：开盘取第一根、收盘取最后一根、高低取极值、量额求和；原生5m用于校验或缺口补采，记录来源。午间及跨日不拼接分钟窗口。
- 盘中缺失集合在当前任务中管理，盘后按证券、交易日、间隔和复权口径统计完整性，不增加逐分钟管理层。Hot保留期、checkpoint及清理由配置与发布门禁决定，本次不启用自动删除或动态分桶。
